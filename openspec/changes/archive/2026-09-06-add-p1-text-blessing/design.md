## Context

见 [proposal.md](proposal.md) 的 Why。技术方向见 [ADR 0003](../../../docs/adr/0003-p1-tech-stack-web-first.md)（Proposed），完整架构见 [P1 架构设计](../../../docs/architecture/p1-architecture.md)。当前仓库无产品代码。P1 是首个产品增量，跨前端 / 后端 / 数据库，且引入内容审核这一可插拔外部能力模式——符合"需要 design.md"的判据。

## Goals / Non-Goals

**Goals:**

- 把"祝福状态机 + 延迟送达 + 坚持记录"这些领域规则做成不依赖框架、可单测、可跨端复用的纯逻辑模块。
- 让"访客免注册看落地页"从第一天起就是任意浏览器可达的普通 Web 页面。
- 内容审核用接口 + 规则实现，验收不依赖真实第三方账号；接口契约按"未来异步"设计。
- "精选展示默认值"等待法务确认的点，做成配置而非硬编码。

**Non-Goals（设计层边界）:**

- 不做审核后台的独立部署 / 独立权限体系（P1 用主应用内路由 + 角色区分）。
- 不做多写库 / 分库分表 / 缓存层设计（P1 单库足够；上亿用户的扩展性留到后续，不提前抽象）。
- 不做真实微信 appid/secret 接入的联调（P1 用可切换的 auth 实现，本地用 stub）。
- 不做 CDN / 边缘缓存失效的具体实现（只在接口层保证"撤回后不返回正文"，缓存策略在部署阶段定）。

## Decisions

### D1: 领域逻辑与 IO 分离

祝福状态机（`lifecycle`）、坚持记录聚合（`streak`）、审核判定映射实现为纯函数模块，输入输出都是普通数据结构，不碰数据库、不碰 HTTP。理由：这些是 P1 最容易出错也最需要回归保护的部分（非法状态转移、计数回撤、跨时区自然日）；纯函数让每条 spec scenario 直接对应一个单测。替代方案（状态机散在 service / ORM 钩子里）被否，原因是难测、难跨端复用（ADR 0003 预留了小程序 / 原生复用的可能）。

### D2: 作者状态 vs 接收方可见性

不引入两张状态表，而是用单一 `state` 枚举 + 一个"接收方是否可见"的纯函数（`isPubliclyVisible(state, expiresAt, now)`）。`verifying` / `rejected` 时链接已存在但 `isPubliclyVisible` 为 false。理由：状态机唯一事实来源只有一处，可见性是它的投影，避免两处状态不一致。

### D3: 落地页接口只返回"占位类型"，不返回正文

`GET /p/:slug` 对非公开可见的祝福只返回一个枚举（`preparing` / `withdrawn` / `taken_down` / `expired` / `not_found`），前端据此渲染中性占位。理由：从接口层杜绝校验期 / 下架内容通过响应体泄露，即使前端有 bug 也不会漏正文。

### D4: 延迟送达 P1 用"提交请求内同步校验"，接口按异步设计

`POST /api/blessings` 内同步调用 `RuleBasedProvider`（本地、毫秒级）得到 `pass/suspect/violation` 并落状态。但返回体不承诺"已发布"，只承诺"已受理"，前端据轮询 / 重新拉取得到最终状态——这样接入真实云 API（异步 + 回调）时前端和接口契约不变。理由：避免为 P1 引入消息队列 / worker 这些"以防将来"的活动部件（AGENTS.md §4.4），同时不让接口契约被"同步"绑死。

### D5: 审核工单统一一张表

自动疑似、举报、申诉都进 `reports` 表，用 `origin` 区分，`priority` 排序。理由：三者的处理流程（进队列 → 人工看 → 出结论 → 驱动祝福状态机 → 留痕）完全一致，拆三张表是重复。

### D6: `blessing_events` 独立审计表

状态转移写入独立的 `blessing_events` 表，而非 `blessings` 上的 jsonb 数组。理由：审计查询（谁在什么时候把哪条祝福下架了）友好，且 append-only 不改历史，契合 AGENTS.md 可追溯性要求。

### D7: 配置项而非硬编码

`featuredDefaultOn`（精选展示默认值）、`bodyMinLen` / `bodyMaxLen`、`linkTtlDays`、`holdTimeoutHours`、`spotCheckRatio` 都是运营可调配置。理由：这些数值 use-cases.md 标为"待定"，做成配置让"待定"不阻塞编码，定了改配置即可。

### D8: streak 的续期不加计数

`expired → published`（续期）不增加坚持记录计数（架构文档 §5 的默认选项）。理由：避免"靠续期刷连续天数"，坚持记录反映的是"当时确实写了"。若评审认为应"恢复原发布日计数"，是配置级调整，不影响 specs。

## Risks / Trade-offs

- [规则审核漏判/误判] → P1 接受较高误判（宁可进人工队列也不放行），并从第一天做随机抽检 + 人工校准集；真实 API 替换是既定路径。
- [同步校验拖慢提交响应] → RuleBasedProvider 是本地字符串匹配，毫秒级；接口契约已按异步设计，真实 API 接入时改为受理即返回。
- [“精选展示默认开”可能不合规] → 已做成配置，默认值切换零代码改动；specs 有对应 scenario；法务结论落 ADR-M。
- [无 CDN 失效方案，撤回后边缘可能仍有缓存] → P1 落地页响应设短 `Cache-Control` / 不缓存正文；真正的边缘失效在部署 ADR 处理。
- [单库无水平扩展] → P1 是 MVP，用户量小；提前分库是过度设计。扩展性在有真实负载数据后再谈。
- [微信 auth 用 stub，联调风险后置] → auth 做成接口，stub 与真实实现同签名；真实 appid/secret 到位后只换实现 + 一轮联调。

## Migration Plan

P1 是全新增量，无数据迁移。部署顺序：建库 + 迁移脚本 → 后端 API → 前端。回滚：P1 未上线前无回滚问题；上线后回滚 = 下线前端入口，祝福数据保留。

## Open Questions

- 生产托管环境（云厂商、域名、对象存储是否需要）——不影响 specs / 任务拆分，部署阶段定。
- 审核后台是否最终独立成单独前端应用——P1 先内嵌，不影响领域逻辑与接口。
- slug 长度与字符集的最终取值——安全下限（不可枚举）已在 specs 表达，具体值实现时定。
