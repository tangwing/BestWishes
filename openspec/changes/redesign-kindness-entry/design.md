## Context

见 [proposal.md](proposal.md) 的「Why」。这里只记实现这条动线时必须先定的技术选择。

当前相关现状（读代码得出，不是推测）：

- `GET /api/plaza` 与 `GET /api/plaza/:id` 已经用 `getUserId()`（可为 null）而不是 `requireUserId()`，**服务端本来就允许访客读**。挡住访客的是前端与首页，不是后端鉴权。
- `wish-request-service.detail()` 对**任何** viewer（含访客）下发 `audioUrl`，但 `audio-scoring-service.readAudio()` 只放行 `b.authorId === userId || b.recipientIds.includes(userId)`。**第三方登录用户在广场点播放必然 403** —— 这是既有的真实缺口，本变更必须一并收口，否则"访客可读 / 登录可听"这条线自相矛盾。
- `WishRequest` 已有写入时维护的聚合字段 `responseCount` / `lastResponseAt`（B-71 建立的 Topic 模式），最新回应摘录沿用同一条写入路径即可，不需要新机制。
- `Compose.tsx` 的 `canSubmit = bodyLen >= 5 && (isReply || (preview?.canSend ?? false))` —— 预览是硬门槛的根，改这一处就解开。
- 协议 gate 已支持 `?returnTo=`（B-72 修的），"登录后回原处"可以复用同一套返回机制，不另造一套。

## Goals / Non-Goals

**Goals:**

- 访客读、登录写、登录听——三档权限在服务端只有一个判定入口，前端不做安全判断（前端只决定显示什么）。
- 最新回应摘录走写入路径维护，列表查询保持 O(页大小)，不随回应数增长。
- "登录后内容不丢"对**所有**提交入口一致生效，不是逐页各写一遍。

**Non-Goals:**

- 不引入客户端状态管理库。保持内容用的是现有的 React 局部状态 + 路由 state。
- 不做访客匿名投稿（写操作一律要登录）。
- 不改 `maxAudienceSize` 的取值与校验位置。
- 不动导航结构（第 3 步的事）。

## Decisions

### D1：未登录内容的保持用 `sessionStorage` + `returnTo`，不用后端草稿

未登录用户没有 `userId`，现有的 `draft-service`（服务端草稿）无处挂载。三个候选：

- **（选中）`sessionStorage` 暂存 + 复用现成的 `?returnTo=` 回跳**：访客点提交 → 把表单内容按页面 key 写进 `sessionStorage` → 跳 `/login?returnTo=<原路径>` →（如需）协议页同样带 `returnTo` → 回到原页面时按 key 取回并清除。零后端改动，零新依赖，和 B-72 已经建好的回跳机制同源。
- 后端匿名草稿（给访客发临时 id）：要新建表、新建过期清理、还要处理"临时草稿归属到登录后账号"，为一个纯前端问题引入持久化状态。
- URL 携带内容：正文可能上千字，且会进浏览器历史与日志，隐私上不可接受。

`sessionStorage` 关标签页即失效，这正好符合"未提交的东西不该长期留存"。**注意**：`sessionStorage` 在隐私模式 / 禁用站点数据时可能抛异常，读写一律包 try/catch，取不到就按空表单渲染——不能因为存不上就让提交流程卡住。

### D2：音频权限判定放在 `readAudio()` 一处，按"这条祝福是不是公开祈福的回应"分流

`readAudio(userId, blessingId)` 的判定扩展为：

1. 作者本人 → 放行（不变）
2. 收件人之一 → 放行（不变）
3. **该祝福 `scope === 'wish_response'` 且其 `requestId` 指向的祈福当前是 `published`** → 任何**登录**用户放行（新增）
4. 其余 → `forbidden`（不变）

第 3 条要多读一次 `wishRequests.findById()`，是本变更唯一新增的一次查询；放在这里而不是路由层，是因为"能不能听"是领域权限，不是 HTTP 关注点，且 e2e 之外的服务层测试也需要覆盖它。

路由仍然 `requireUserId()` —— 访客拿不到音频这件事由路由挡，`detail()` 只负责**不下发链接**。两层各司其职：路由挡访问，视图挡泄露。

**替代方案（否决）**：给音频发带签名的临时 URL 让访客也能听。签名 URL 会绕开登录墙，等于把"音频需登录"这条产品决策架空；而且它会让 B-93 遗留的 `/p/:slug` 权限问题从"待定"变成"已经错了"。

### D3：最新回应摘录 = `wish_requests.last_response_excerpt` 冗余列，与 `lastResponseAt` 同事务写

摘录随 `responseCount` / `lastResponseAt` 在同一处维护（回应发布、撤回、下架都已经走那条路径）。撤回场景需要"退回到上一条"，这时 MUST 去查该祈福剩余的最新一条 `published` 回应——**只有撤回 / 下架这类低频路径才付这次查询**，正常发布路径不查。

摘录长度在写入时截断（建议 60 字），音频回应取 `media.transcript`；转写为空时摘录为空但 `responseCount` 照加——不能因为没有转写就让这条回应在列表上"消失"。

**替代方案（否决）**：列表查询时 join 最新回应。100M 规模下这是典型的 N+1 / 大排序，也和 B-71 已经确立的"聚合字段写入时维护"模式冲突。

### D4：匿名是展示层遮蔽，不是存储层脱敏

`wish_requests.anonymous` 只在**组装视图**时生效（`plaza()` / `detail()` / 匹配通知的文案）。`authorId` 照常存、照常索引。理由：审核工单、撤回、收回应、以及将来任何追责都需要真实作者；一旦在存储层脱敏，这些全部失效，且不可逆。

遮蔽必须在**服务端**做——不能把 `authorNickname` 发给前端再由前端选择不显示，那等于没有匿名。

匿名 MUST 在发布时定死：已经公开的内容中途换身份，会让看过的人前后看到两个不同的作者。

### D5：默认受众条件的唯一来源放 `packages/shared`

`DEFAULT_FILTER` 目前只在 `Compose.tsx` 里。服务端在提交时也要有一份"用户没给条件时用什么"的判断，两边各写一份必然漂移。放 shared 里导出一个常量，前后端同引。

默认值取**近距离 + 其余全空**：年龄 / 性别 / 标签任意一项非空，都会把画像不全的人排除掉（这是 `user-profile` 既有行为，B-83 排查过的那个坑）。冷启动阶段用户画像普遍不全，默认带上任何一项都会让新用户命中 0 人。

## Risks / Trade-offs

- **[撤回摘录退回的一致性] 最新回应被撤回时若摘录没更新，列表会展示已撤回内容的文字** → 摘录的更新必须和 `responseCount` 的回退在同一个写入路径、同一事务里；补一条专门的回归测试（撤回最新回应后列表摘录变成第二新的那条）。
- **[访客可读扩大了暴露面] 祈福内容此前只有登录用户能看，现在全网可读** → 匿名发布（D4）是对冲手段；另外 `pending_review` 的祈福本来就不进广场，这条不变。仍要注意：**这是一次不可逆的公开范围扩大**，已经发布的存量祈福会因此从"登录可见"变成"全网可见"，上线前需要产品侧确认是否要对存量数据做一次告知或默认匿名化。
- **[sessionStorage 不可用] 隐私模式下内容保持会失效，用户登录回来发现要重写** → try/catch 包住，失败时不阻断流程；并且登录跳转前若存储失败，给一句"登录后可能需要重新输入"的提示，而不是静默丢失。
- **[取消预览硬门槛后，命中 0 人的失败从"发送前"挪到"发送后"]** → 服务端 `audience_empty` 的错误文案要足够具体（当前条件命中 0 人 + 怎么放宽），且必须显示在提交按钮附近而不是长表单底部（B-50 的教训）。
- **[2 步路径的可验收性] "至多 2 次主动操作"是个容易在后续迭代中被悄悄破坏的约束** → 用 e2e 把它钉死：一条从首页出发、只点两次就送出的用例，任何人加了新的必经步骤都会让它变红。

## Migration Plan

1. 一次迁移加 `wish_requests.anonymous`（默认 false）与 `last_response_excerpt`（可空）。两列都可空 / 有默认值，旧行不需要回填。
2. `last_response_excerpt` 对存量祈福为 null——列表显示"还没有回应"，与实际 `responseCount > 0` 不一致。上线时跑一次性回填脚本（按 `responseCount > 0` 的祈福补摘录），或接受存量数据在收到下一条回应后自愈。**建议回填**，否则广场首屏在上线当天全是空摘录，正好毁掉本变更的目的。
3. 回滚：两列可空、判定逻辑向后兼容，回滚前端即可恢复旧行为，不需要回滚数据库。

## Open Questions

- 首页展示"哪一条"祈福：最新一条、还是最近有回应的一条、还是随机一条？三种都满足 spec（spec 只要求"至少一条真实的 `published` 祈福"）。倾向"最近有回应的一条"——它最能同时展示需求与善意两侧，但这是可以上线后按数据调的策略，不影响本变更的接口与任务拆分。
- 摘录截断长度（60 字是初值）同理，属可调参数。
