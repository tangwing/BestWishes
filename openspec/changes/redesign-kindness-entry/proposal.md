## Why

2026-09-13 的阶段性复盘（见 PROMPT_LOG.md）发现：理念 → 领域模型 → 后端能力这条链路是好的，但**理念 → 用户此刻的感受**这条链路还没建。把当前 Demo 的首次善意路径从代码里数出来，是 **9 步、跨 4 个页面**：

> 首页（未登录看不到任何一条真实善意）→ 登录 → 点「传递善意」→ 被重定向到协议页 → 同意 → 回到 `/give` → 选受众 → **手动点一次「预览命中人数」**（`Compose.tsx` 的 `canSubmit` 强依赖 `preview.canSend`）→ 选形式 → 选场景 → 写正文 → 发送

这 9 步里**没有任何一步让用户看到"有个具体的人此刻需要这份祝福"**——用户是在对着一个人口筛选器写信。vision.md 的使命第一个动词是「**激发**」，而现在的产品假设用户自带善意进来，只给他一套工具。

能激发的东西其实已经建好了，就是祈福广场；它被放在动线的旁边，而不是入口。本变更只做一件事：**把首次善意的成本降到最低，把激发前置到第一屏**。

## What Changes

- **新增「入口动线」能力**：定义首页对访客和登录用户分别呈现什么、首次善意的最短路径、以及登录发生的时机。核心约束是**首页 MUST 呈现至少一条真实的、公开的祈福及其最新一条回应原文**，并就地提供回应入口；登录 MUST 推迟到提交内容的那一刻，MUST NOT 作为浏览与撰写的前置。
- **BREAKING（对 spec，不对用户）：撤销「广场列表 MUST NOT 包含任何回应正文」**。这条是 B-71 定的"论坛正确"约束，它把产品最有情绪能量的东西（别人给陌生人写的那段真诚的话）藏在了详情页里。改为列表 MUST 展示**最新一条回应的摘录**；完整回应列表仍然只在详情页。
- **访客可读，读到文字为止**：祈福正文、标签、全部文字回应与往返回复，未登录访客 SHALL 可读；**音频回放 MUST 要求登录**。顺带修掉一个真实的权限缺口——详情视图对所有人下发 `audioUrl`，但音频路由只放行"作者或收件人"，第三方点播放必然 403。权限模型改为：广场上 `published` 的回应音频，**任何登录用户**可播放。
- **匿名发布祈福**：撰写祈福时可勾选匿名，广场与详情显示为"一位朋友"，不露昵称 / 城市。后台仍关联真实 `authorId`（审核、撤回、收回应全部不受影响）。公开可读之后，写下自己的处境是全站暴露感最强的动作，这是降低需求侧门槛的直接手段。
- **受众预览从硬门槛降级为可选辅助**：群发不再要求"必须先点一次预览才能发送"。撰写页 SHALL 带一组可用的默认受众条件，用户不碰筛选器也能直接写、直接发；人数上限的校验仍在提交时由服务端执行（`[1, maxAudienceSize]` 的约束一个字不改）。

### 非目标（本变更明确不做）

- 可分享的祝福卡、og:image、微信 JS-SDK 分享、把用心反馈接到文字祝福——全部是第 2 步（`add-shareable-blessing-card`）。
- 底部 tab 导航、PWA、Web Push——第 3 步（`add-mobile-shell-pwa`）。本变更不动导航结构，只改各页内容与门槛。
- 视频形态、悬赏、真实 ASR 接入——仍分别在 P3 / 未定。
- 访客**写**祈福或回应（匿名浏览可以，匿名投稿不做：失去审核与撤回的落点）。

## Capabilities

### New Capabilities

- `kindness-entry`：入口动线——首页对访客 / 登录用户的呈现、首次善意的路径长度约束、登录时机（提交那一刻）与提交前内容的保持。

### Modified Capabilities

- `wish-request`：「祈福广场列表」撤销"列表 MUST NOT 含回应正文"，改为 MUST 含最新一条回应摘录 + 明确访客可读；「查看祈福详情」明确访客可读文字、音频需登录，并把音频回放的权限模型从"作者或收件人"放宽到"任何登录用户可播放广场公开回应"；「撰写祈福」新增匿名发布选项。
- `wx-account`：「访客无需账户」的可见范围从"被分享的祝福链接"扩展到"祈福广场列表与详情的文字内容"，并明确音频回放属于要求登录的操作。
- `blessing-audience`：「受众预览」从"发送的前置步骤"降级为可选辅助，新增"撰写页的默认受众条件"，使不碰筛选器也能完成群发。

## Impact

- **领域层**（`packages/domain`）：`WishRequest` 加 `anonymous: boolean`；默认受众条件的常量与合法性校验放纯函数层（`audience.ts` 旁）。
- **共享层**（`packages/shared`）：`submitWishRequestSchema` 加 `anonymous`；`AudienceFilter` 的默认值来源统一到 shared，避免前后端各写一份。
- **服务端**（`server/`）：`wish-request-service.plaza()` 的列表项加"最新一条回应摘录"（用已有的 `lastResponseAt` 同一条写入路径顺带维护 `lastResponseExcerpt`，**不在列表渲染时扫全表**）；`detail()` 对匿名祈福遮蔽作者信息、对未登录访客不下发 `audioUrl`；`audio-scoring-service.readAudio()` 的权限判定改为"作者 / 收件人 / 任何登录用户（当该祝福是 `published` 的祈福回应时）"；`blessing-service` 提交群发时不再依赖客户端预览结果。
- **前端**（`client/`）：`Home.tsx` 重做为"一条真实祈福 + 就地回应入口"；`WishRequests.tsx` 列表项展示最新回应摘录；`WishRequestDetail.tsx` 访客可读、音频位显示"登录后可收听"；`PublishWishRequest.tsx` 加匿名勾选；`Compose.tsx` 受众筛选器折叠 + 默认值 + 去掉预览硬门槛；未登录用户写完内容点发送时，内容 MUST 在跳登录并返回后仍在。
- **数据层**：`wish_requests` 加 `anonymous`、`last_response_excerpt` 两列（一次迁移）。
- **测试**：广场列表摘录的写入维护、匿名遮蔽、访客可读 / 音频 403→登录后 200 的权限矩阵、"不碰筛选器直接发"的群发路径；e2e 补一条"未登录访客从首页读到一条回应 → 点回应 → 登录 → 内容未丢 → 发出"。
- **不涉及**：`content-moderation`（匿名不改审核，工单仍指向真实作者）、`blessing-delivery` 的投递与状态机、`notification`。
