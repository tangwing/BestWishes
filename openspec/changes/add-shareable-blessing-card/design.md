## Context

见 [proposal.md](proposal.md) 的「Why」。这里只记实现这件事必须先定的技术选择——其中"卡片图片怎么生成"是本变更唯一的重量级决策，**必须先定再写代码**。

约束与现状：

- 卡片上是**中文**。服务端渲染中文必须自带字体文件，不能依赖宿主机装了什么字体（容器里通常一个中文字体都没有，渲染出来是一排豆腐块）。
- 产品视觉是米色 / 宋体 / 克制（`client/src/styles/theme.css`），卡片必须和它是同一套东西，否则分享出去的产物看着不像这个产品。
- `@fastify/multipart` + 本机落盘的音频存储 port 已经存在（P2 建的），卡片缓存可以挂在同一个抽象后面，不需要新建存储概念。
- AGENTS.md §4.4「依赖即永久代码」：加依赖要说明为什么。本变更会加**一个**运行时依赖，理由见 D1。
- 微信分享的完整能力（JS-SDK 自定义分享卡片）需要公众号 appId + **已备案域名**；ICP / 公司主体仍是 B-42 未办的事项。这直接决定了 D3 的范围。

## Goals / Non-Goals

**Goals:**

- 卡片是确定性的派生物：同样的祝福内容生成同样的图，可缓存、可重算、**不进数据库**。
- 卡片的视觉与产品同源，改主题色不用改两份。
- 文字反馈复用 `audio-scoring` 已有的可插拔评估器，**不新建第二套评分体系**。
- 在拿不到微信 appId 的前提下，分享依然可用（降级路径必须是完整体验，不是残疾体验）。

**Non-Goals:**

- 不做卡片模板 / 配色 / 贴纸的自定义。
- 不引入无头浏览器到生产运行时。
- 不为卡片建表、不做版本历史。
- 不做分享的埋点统计（B-87 待讨论）。

## Decisions

### D1：卡片 = 零依赖生成 SVG + 一个光栅化依赖，服务端渲染

分四步：把祝福数据排成一份 SVG 字符串（纯字符串模板，零依赖，颜色 / 字号直接引产品的设计 token）→ 光栅化成 PNG → 落盘缓存 → 按 URL 提供。

候选方案：

| 方案 | 取舍 |
|---|---|
| **（选中）手写 SVG + `@resvg/resvg-js` 光栅化** | 一个依赖。版面是我们自己的字符串模板，和 `theme.css` 的 token 手动对齐容易；resvg 支持嵌入字体文件。代价：**SVG 没有自动换行**，中文断行要自己写（见 D2）。 |
| `satori` + `resvg` | satori 把 JSX 布成 SVG，自动换行是白送的；但它引入两个依赖 + 一套 JSX-in-server 的写法，且 flex 子集有不少坑。为省一个断行函数换来两个依赖和一层新范式，不划算。 |
| `@napi-rs/canvas` 命令式绘制 | 一个依赖，`measureText` 让断行更准。但版面是命令式代码，和 CSS 的对应关系全靠人脑维护，改视觉时最容易漂。 |
| 无头浏览器截图 | 复用得了 Playwright（已是 e2e devDependency），但把浏览器塞进生产运行时，内存和冷启动都是数量级的代价。**明确否决。** |

**字体**：服务端捆一份思源宋体（Noto Serif SC）供 resvg 嵌入。这是 MB 级的二进制资产，必须显式确认它进不进 git（建议进，版本固定、可复现，和"依赖即永久代码"的取舍一致）；只在服务端用，不下发给浏览器。

### D2：中文断行自己写，按字符宽度估算而不是精确测量

SVG 没有 auto-wrap。断行规则：CJK 字符逐字可断；连续的拉丁字母 / 数字作为整体不拆；标点不能出现在行首（避头尾）。宽度按"CJK 算 1 个字宽、拉丁算 0.5 个"估算——卡片版面是我们自己定的，留够边距，估算误差不会溢出。

**不做**精确 `measureText`：那要么引入 canvas（多一个依赖），要么解析字体表（大量代码）。这是一张卡片，不是排版引擎。

断行是纯函数，必须单测：纯中文、纯英文长单词、中英混排、连续标点、超长到需要截断。

### D3：微信分享分两层，第一层不依赖 appId

- **第一层（本变更做）**：落地页输出 `og:title` / `og:description` / `og:image`（指向卡片）+ `twitter:card`，并保证卡片图**在 HTML 里靠前出现**。微信在没有 JS-SDK 配置时，分享预览会自行抓取页面标题与靠前的图片——所以第一层已经能在微信里得到像样的预览，且在所有其它渠道（浏览器、iMessage、Slack…）都成立。
- **第二层（本变更不做，留任务但标为阻塞）**：JS-SDK `updateAppMessageShareData` 自定义分享标题 / 描述 / 图标。它需要公众号 appId + secret + **已备案域名**做签名，而 ICP 仍是 B-42 未办事项。**在拿到这些之前无法真机验证，写了也是不可验证的代码**——AGENTS.md §2「不做无法验证的工作」。

这样分层的好处：分享能力今天就能上线并验证，不被合规资质卡住。

### D4：文字反馈复用现有评估器，只换维度集合

`audio-scoring` 的管线里，真诚度 / 个性化评估本来就是对**转写文本**做的（`RuleBasedSincerityEvaluator`），并不依赖音频。文字祝福走的是同一个输入形态——一段文本。

所以：**复用同一个 provider 接口**，只是不跑音频信号那一段（`audio-signals.ts` 的停顿 / 语速，文字里没有依据），完整性判定复用 `isLowEffort` / `looksGarbled`。输出结构与音频反馈同构（多维标签 + 置信度），前端可以共用展示组件。

这不是"把音频打分搬到文字上"，而是**把本来就作用于文本的那部分拿出来单独用**。

### D5：反馈是发送流程之外的一步，失败不回滚

反馈生成 MUST NOT 阻断发送（spec 硬约束）。实现上：祝福先落到 `published` 并完成投递，反馈单独产出；反馈失败 / 超时时结果页显示"反馈暂不可用"，祝福已经发出去了。

这和 `audio-scoring` 的现状一致（那条管线全同步，但它的失败同样不回滚投递）。**不要**为了拿到反馈而把发送改成"等反馈出来再送达"——那直接违反 vision 的"祝福始终送达"。

### D6：卡片缓存的 key 与失效

key = 祝福 id + 其内容与展示字段的哈希（正文、昵称、城市、场景）。内容变了 key 就变，天然免去主动失效。缓存 miss 就现生成。

状态变化（撤回 / 下架 / 过期）**不走缓存失效**——请求卡片时先查祝福当前状态，非 `published` 直接返回中性占位，根本不碰缓存。这样"撤回后卡片还能被拿到"这类泄露不可能发生。

## Risks / Trade-offs

- **[中文字体是 MB 级二进制] 进仓库让 clone 变重，不进仓库则部署多一步且容易漏** → 建议进仓库并固定版本（可复现优先）；在 README / 部署说明里写清它的用途，避免后人当成误提交删掉。
- **[断行估算不精确，长正文可能贴边] ** → 版面留足边距 + 截断阈值保守；单测覆盖中英混排与超长；视觉走查时专门看最长的那条。
- **[og:image 缓存被第三方长期持有] 分享出去后，即使祝福被撤回，已经抓取过预览图的平台可能仍展示旧图** → 这是外部平台行为，产品侧无法收回。落地页本身会立刻变成占位（D6），但**分享预览图可能滞留**——这个事实必须写进「已分发副本不可追回的告知」的用户沟通里（该 Requirement 已存在，本变更不改它，但实现时要确认文案覆盖了这一情形）。
- **[卡片让"分享"这件事有了真实的隐私后果]** 收件人分享收到的祝福 = 把发送者写的话公开。落地页本来就是公开的，所以可见性没有扩大——但**心理上**"我写给一个陌生人的话被做成图片传播"是新的感受。上线前值得在发送页用一句话说清楚（"这条祝福有公开链接，对方可以分享它"）。
- **[反馈维度太少会显得敷衍]** 文字能支撑的维度确实比音频少。宁可少而准，也不要为了凑数把音频维度硬套过来——那会立刻被用户识破为假反馈，比没有反馈更伤。

## Migration Plan

1. 加依赖（光栅化库）+ 字体资产，`pnpm verify` 绿。
2. 卡片生成与缓存上线——纯新增路径，不影响任何既有行为，可独立部署。
3. 落地页补 meta 与音频入口——改的是 `/p/:slug` 的渲染，状态占位规则不动；回滚 = 去掉 meta 标签。
4. 结果页改版——最后上，因为它同时依赖卡片与反馈。
5. 回滚策略：三块互相独立，任一块出问题单独回滚，不会把其它两块拖下水。

## Open Questions

- 卡片尺寸比例（方形便于朋友圈九宫格，竖版便于聊天窗口全屏）——两者都满足 spec，可上线后按实际分享渠道调整，不影响接口与任务拆分。
- 字体最终选哪一款开源中文衬线（思源宋体是默认倾向）——影响视觉不影响结构。
