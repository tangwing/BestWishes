## Why

见 2026-09-13 复盘（PROMPT_LOG.md）：产品使命是"激发并**传递**全世界的善意"，但**传递这一条在产品层几乎没有被实现**。现状只有一个 `/p/:slug` 朴素网页——没有 og:image、没有微信分享、没有任何用户会想发出去的产物。一个以传播善意为使命的产品，缺少它唯一的病毒载体。

同时，给予方的回报是断的：P1 文字群发发出去就石沉大海，可能永远等不到回音。vision.md 承诺"**用心反馈**（给祝福者）：帮助表达得更专注、更完整，**始终提供**"——这套管线（`audio-scoring`）已经建好了，却只接在音频回应上，**文字祝福一条反馈都没有**。"送人玫瑰、手有余香"里的"余香"，目前只在音频路径上兑现了。

这两件事是同一件事的两面：**第一次给予之后的那 5 秒钟，用户要么拿到点什么，要么就走了。** 本变更负责这 5 秒。

## What Changes

- **新增「祝福卡」能力**：任何一条 `published` 的祝福 SHALL 可生成一张视觉化的祝福卡（正文 + 来源的粗粒度信息 + 场景），可保存为图片、可分享。卡片 MUST 复用产品既有的视觉调性（米色 / 宋体 / 克制），MUST NOT 暴露 openid、精确位置、手机号。这是本变更的增长载体。
- **新增「用心反馈（文字）」能力**：文字祝福提交后 SHALL 立刻得到多维的用心反馈，兑现 vision 的"始终提供"。反馈 MUST 沿用 `audio-scoring` 已确立的输出契约——**多维标签 + 置信度，绝不是单一分数，绝不打负面标签**；不含依赖音频信号的维度（专注度 / 流畅度来自停顿与语速，文字里不存在）。反馈 MUST NOT 影响是否送达（vision 硬约束：祝福始终送达）。
- **落地页升级为传播载体**：`/p/:slug` SHALL 输出 og / 微信所需的分享元信息（标题、描述、`og:image` 指向该祝福的卡片），并补上**音频祝福的播放器**——这是 B-93 明确遗留的缺口（落地页至今只显示转写文字，音频听不了）。落地页的访客可见性与状态占位规则不变。

### 非目标（本变更明确不做）

- 不做"把别人送我的祝福以我的名义分享"之外的任何再创作、合成、拼接（P5）。
- 不接真实云 ASR / 云 LLM。文字反馈复用 `RuleBasedSincerityEvaluator` 既有的可插拔实现，和 P2 一样默认走规则实现，真实模型是后续替换 provider 的事。
- 不做卡片的自定义模板、配色、贴纸。一套模板，做好。
- 不做分享数据的埋点统计——trace / 分析系统整体待讨论（AGENTS.md §6，B-87），本变更不预先实现。
- 不做微信 JS-SDK 的自定义分享（需 appId + 已备案域名，见 Impact）。
- 不动导航与移动端形态（第 3 步）。

## Capabilities

### New Capabilities

- `blessing-card`：祝福卡的生成、内容构成、隐私约束、可保存 / 可分享的产物形态，以及它作为落地页 `og:image` 的来源。
- `blessing-feedback`：文字祝福的用心反馈——多维标签输出、始终提供、不影响送达、不打负面标签。

### Modified Capabilities

- `blessing-delivery`：「可分享的祝福落地页」补充分享元信息（og / 微信）与音频播放器（B-93 遗留缺口），状态占位与隐私规则不变。

## Impact

- **领域层**（`packages/domain`）：文字反馈的规则层纯函数（复用现有 `isLowEffort` / `looksGarbled` 与真诚度评估的可插拔接口，**不新建一套评分体系**）；卡片的文案排布是纯数据到纯数据的变换，可单测。
- **服务端**（`server/`）：新增卡片图片的生成与缓存（一条祝福的卡片是确定性的，生成一次即可复用）；`/p/:slug` 的 HTML 响应补 meta 标签；音频回放在落地页的权限模型——落地页免登录而音频要求登录（沿用第 1 步 `redesign-kindness-entry` 定下的三档权限），落地页对访客给"登录后可收听"。
- **前端**（`client/`）：发送成功页从"一句话确认"变成"卡片 + 用心反馈 + 分享入口"；`Sent.tsx` / `AudioFeedback.tsx` 的成功态统一到这一个产物上；微信环境下调用 JS-SDK 配置分享卡片（非微信环境正常降级，落地页本来就不依赖微信环境）。
- **依赖新增**：一个服务端图片光栅化库 + 一份服务端中文字体资产（候选与取舍见 design.md D1——这是本变更唯一的重量级技术决策，**必须先定再写代码**）。**微信 JS-SDK 不在本变更内**：它需要公众号 appId + 已备案域名做签名，而 ICP / 主体仍是 B-42 未办事项，写了也无法真机验证（AGENTS.md §2「不做无法验证的工作」）。本变更做的是 og 元信息那一层——它在微信的链接预览、普通浏览器、以及其它所有渠道都成立，不被合规资质卡住。
- **数据层**：卡片是可再生成的派生物，**不进数据库**；缓存落在与音频同一个存储 port 后面（本机落盘 / 生产换对象存储，沿用既有"换驱动不换契约"模式）。
- **基线依赖**：本变更假定 `redesign-kindness-entry` 已 apply——它定下了"访客读 / 登录写 / 登录听"的三档权限，落地页的音频播放器直接沿用，不重新定义。
- **不涉及**：`content-agreement`（作者分享自己的祝福、收件人分享收到的祝福，都在「可分享的祝福落地页」既有的授权范围内，用途分层不变）、`content-moderation`、投递与状态机。
