## Context

见 [proposal.md](proposal.md) 的「Why」。这里只记外壳与推送通道必须先定的技术选择。

约束与现状：

- `App.tsx` 的顶栏是 `.topbarTop`（品牌 + 用户名）+ `.nav`（6 个 13px 文字链接、`flex-wrap`）。B-86 刚把用户名从 nav 中间挪到右上角——**外壳这次要动的正是这块刚修过的结构**，改的时候别把那次修复推翻。
- `app.module.css` 的 `.app` 是 `max-width: 640px` 居中：手机上等于全宽，桌面上是一根细长条。
- 未读数现在靠 `App.tsx` 里一个 4 秒的 `setInterval` 轮询 `api.notifications()`。推送上线后这个轮询还要不要留，是本变更要定的（见 D3）。
- `notification` 能力的 Purpose 原文就写着"真实推送通道（微信模板消息 / Web Push）留到后续"——本变更认领 Web Push 这一半，微信模板消息仍推迟（需公众号资质，B-42）。
- ADR 0003 定的是 Web-first PWA。本变更是**兑现** ADR 0003 里 PWA 那个词，不是新决策，不需要新 ADR。

## Goals / Non-Goals

**Goals:**

- 外壳改动**只动外壳**：导航位置、版面尺寸、安装与推送通道。任何业务规则、任何页面内容逻辑都不在范围内。
- 推送是站内通知的**附加送达手段**，永远不能成为它的前提。
- 在 iOS 这个最受限的目标上先确认可行，再谈别的。

**Non-Goals:**

- 不做原生 / RN / 小程序（proposal 已明确，这里重申是因为它是本变更最容易被"顺手扩大"的边界）。
- 不做离线写入与冲突合并。
- 不重构 CSS 体系、不引入 UI 框架。手机化靠调既有的 `app.module.css`，不换一套。
- 不动 `max-width: 640px` 在桌面上的表现（桌面体验是另一个话题，不在本变更）。

## Decisions

### D1：底部导航是一个新的布局层，不是把 `.nav` 挪个位置

`.nav` 现在是 6 个等权文字链接。底部 tab 只能放 4 个主要去处（广场 / 传递善意 / 我的福袋 / 个人空间），剩下的要有去处：

- **首页：并入广场 tab**（2026-09-13 用户已拍板）。`redesign-kindness-entry` 把首页做成了"一条真实祈福 + 就地回应"，它和广场是同一件事的两个粒度；底部第一项就是广场，打开即那条被选中的祈福，下面接列表。**独立的 `/` 路由不再作为一个去处存在**——这也意味着 `kindness-entry` 里"首页 MUST 呈现……"的措辞要改成不绑定路由的表述（本变更带一个 `kindness-entry` 的 MODIFIED delta 做这件事），否则 spec 和实现当场对不上。代价是首页那种"单条聚焦"的情绪强度会被下面的列表稀释，实现时要保证**被选中的那条在视觉上明显重于列表项**，不能退化成"列表第一项加粗"。
- **审核台**：它本来就不该在主导航上（`add-moderation-rbac` 那个 change 的核心就是"现在任何登录用户都能进审核台"）。**从主导航移除**，改为管理员在个人空间里的入口。这不需要等 RBAC 落地——移除一个入口不会让权限变松，只是不再对所有人显眼。
- **退出**：挪进个人空间，那才是它该在的地方。

所以这不是"把一行 flex 从上面搬到下面"，而是**重新决定哪些东西配得上主导航**。

### D2：响应式断点只设一个，桌面保持现状

移动视口（≤ 一个断点）走底部导航，其上保持现在的顶部导航。一个断点，不做平板中间态——没有证据说明平板需要第三套布局，加了就是三份要维护的版面。

`.app` 的 `max-width: 640px` 在移动端本来就不生效（屏幕更窄），不动它。底部导航要处理 iOS 的安全区（`env(safe-area-inset-bottom)`），否则在带 Home Indicator 的机型上会被盖住——这是最容易漏、且只有真机看得见的一处。

### D3：推送上线后，站内轮询保留

轮询（4 秒一次）是唯一在**所有**情况下都成立的机制：用户没授权推送、推送被系统静默、iOS 没装到主屏——这些都是常态而不是边缘。推送是锦上添花，轮询是地板。

两者都存在时以站内数据为准（推送只是"去看看"的提示，未读数始终从接口来），不会出现推送说有 3 条、站内显示 1 条的错乱。

**替代方案（否决）**：推送上线后关掉轮询。会让未授权用户的未读徽标彻底失效——把一个可选增强变成了必需依赖，方向反了。

### D4：推送发送挂在通知产生点旁边，失败彻底吞掉

在 `notification-service` 产生通知之后发推送，**包在不会向外抛的边界里**：推送失败只记日志，不影响通知落库、不影响投递、不影响调用方的返回。

这是 spec 的硬约束（"推送发送失败 MUST NOT 影响站内通知的产生与未读计数"）落到实现上的样子。端点返回 410 / 404 时删掉该订阅——这是 Web Push 协议规定的"用户卸载了 / 撤销了"的信号，必须处理，否则订阅表会长期堆着死端点。

VAPID 密钥对是**配置**（环境变量），不是代码，也**不能进仓库**。缺配置时推送整体降级为不可用，站内一切照常——这条要有测试。

### D5：推送文案只说类型，不说内容

推送在锁屏上可见，可能被旁人看到。"有人给你送了一段祝福"是安全的；祝福正文不是。这条已经写进 spec，实现上要保证**文案的拼装处拿不到正文**（传 id 和类型，不传内容），而不是靠写文案的人自觉。

### D6：Service Worker 只缓存公开静态资源与已访问的公开页面

缓存范围：应用外壳（HTML / CSS / JS / 图标 / 字体）+ 已访问过的**公开**页面（广场列表、祈福详情的文字、落地页）。

**不缓存**：任何带登录态的响应（福袋、个人资料、音频、发件箱）。理由不只是隐私——共用设备上另一个人打开就能看到，这比"缓存过期"严重得多。

实现上按请求路径与是否携带会话区分，**默认不缓存**，只对显式列出的公开路径缓存。白名单而不是黑名单：漏掉一条白名单只是少缓存一个页面，漏掉一条黑名单就是泄露。

## Risks / Trade-offs

- **[iOS Web Push 的门槛很高]** 需要 iOS 16.4+，且**必须先"添加到主屏幕"**才能请求授权。这意味着在 iPhone 上，推送的转化链是"访问 → 装到主屏 → 授权 → 才收得到"，每一步都掉人 → 不要把任何功能建立在推送必达的假设上（D3 的轮询就是这个前提的产物）；真机验证只能人工做（同 B-69 的 Safari 复测）。
- **[Service Worker 的缓存会让"改了没生效"变成常态]** 开发与演示时最容易踩 → 注册时就定好更新策略（新版本可用即激活并提示刷新），并在 `docs/DEMO.md` 写清"看不到改动先清一次 SW"。**这一条不写下来，后面每一轮走查都会浪费时间在假 bug 上。**
- **[底部导航把审核台移出主导航，可能被读成"权限问题已解决"]** → 不是。移除入口只是不显眼，`add-moderation-rbac`（B-65）仍然待评审；实现时在代码注释里写明这一点，避免后人以为已经有门禁了。
- **[外壳改动会碰到 B-86 刚修的顶栏结构]** → 改之前先看一眼那次提交的意图（用户名要在右上角），别在重排时又把它推回 nav 中间。
- **[390px 走查是人工活，容易只看首页]** → 用 Playwright 设 390px viewport 把主要页面逐个截图，作为可重复执行的走查，而不是靠人记得看哪些页。

## Migration Plan

1. 底部导航 + 响应式断点先上——纯前端，可独立回滚。
2. `manifest.json` + 图标 + Service Worker 次之。**SW 一旦上线，回滚要额外发一版能自我注销的 SW**（旧 SW 会留在用户浏览器里），这是本变更唯一"回滚比上线复杂"的部分，上线前确认注销路径可用。
3. 推送最后上：先订阅存储与清理，再接发送点。VAPID 缺配置时整体降级，可以先部署代码后配密钥。
4. 顺序上三块互不依赖，但推送依赖 SW 已注册（Web Push 走 SW 接收），所以 2 必须在 3 之前。
