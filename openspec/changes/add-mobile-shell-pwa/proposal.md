## Why

见 2026-09-13 复盘（PROMPT_LOG.md）。用户问的是"是不是该现在做移动端 App"，结论是**现在不做原生，但必须现在做手机形态**——两件事经常被混为一谈：

- 原生 / RN 化是把**当前这套动线**搬进另一个容器。动线本身还没验证过，搬过去只会让未验证的假设更难改。
- 而真正缺的"手机形态"——拇指可及的导航、可安装到主屏、真实推送——**在现有 Web 栈里全部拿得到**（B-27 已经在 BACKLOG 里躺着）。

现状是一个排版良好的网页，不是一个 App：顶栏 6 个 13px 文字链接 + `flex-wrap`，手机上会折成两行小字、且**全部在拇指够不到的顶部**；没有 `manifest.json`、没有 Service Worker、不能加到主屏；`notification` 能力的 Purpose 里白纸黑字写着"真实推送通道（微信模板消息 / Web Push）留到后续"——那个"后续"就是现在。没有推送，"有人给你送了祝福"这件事只有用户主动打开才知道，回赠率无从谈起。

这是三步里的最后一步：前两步把回路和产物做出来，这一步让它长成手机上的样子，然后用它去量三个数（打开→首次善意转化率、收到→24h 回赠率、外链带新占比）。

## What Changes

- **新增「移动端外壳」能力**：底部固定导航（拇指区），可安装（`manifest.json` + Service Worker + 图标），以及移动优先的版面约束——内容区 MUST 不产生横向滚动，主要操作 MUST 落在屏幕下半部分。顶部只保留品牌与未读提示。
- **推送通道**：`notification` 新增 Web Push——用户 SHALL 可授权接收推送；收到祝福 / 祈福回应时 SHALL 推送。授权 MUST 是可选的、可撤销的，拒绝授权 MUST NOT 影响任何既有功能（站内未读徽标照常工作）。推送内容 MUST NOT 包含祝福正文（隐私：锁屏可见）。
- **导航入口从顶栏迁到底部**：`blessing-records` 的「收件箱入口」现在写死"**顶部**导航 SHALL 有一个……"，与底部 tab 直接冲突，需要改为不绑定位置的表述。
- **离线兜底**：Service Worker MUST 为已访问过的页面提供离线可读的降级，MUST NOT 缓存需要登录才能看的内容。

### 非目标（本变更明确不做）

- **不做原生 / React Native / 小程序**。多端原生实现方式仍是 AGENTS.md §6 的未决项，需要先有留存数据再谈，本变更 MUST NOT 替它拍板。
- 不做微信模板消息（同 `add-shareable-blessing-card` 的理由：需公众号资质 + 备案域名，B-42 未办，写了无法验证）。
- 不做离线**写入**（离线排队发送、冲突合并）——复杂度高、价值未验证。离线只保证"读得到"。
- 不改任何业务动线与内容规则（那是前两步的事）。
- 不做埋点 / 分析系统（B-87 待讨论）——本变更让三个数**可被观测**是产品侧的事，实现待那个讨论有结论。

## Capabilities

### New Capabilities

- `mobile-shell`：移动端外壳——底部导航、可安装性、移动优先版面约束、离线读降级。

### Modified Capabilities

- `notification`：新增 Web Push 推送通道（授权可选可撤销、拒绝不降级既有功能、推送内容不含正文）；「未读数与标记已读」的站内机制不变。
- `blessing-records`：「收件箱入口」从"**顶部**导航 SHALL 有一个入口"改为不绑定具体位置的表述——入口与未读徽标的行为不变，只解除对"顶部"的绑定，让底部 tab 成为合法实现。
- `kindness-entry`：首页并入广场 tab（2026-09-13 用户拍板），「首屏呈现真实的善意」与「首次善意的最短路径」里"首页"的措辞改为不绑定路由的"入口页"；并新增一条约束——入口页同时展示选中祈福与列表时，被选中的那条 MUST 在视觉上明显更重，防止合并后退化成一个无重点的列表。

## Impact

- **前端**（`client/`）：`App.tsx` 的顶栏拆成"顶部只留品牌 + 未读"与"底部 tab 导航"；全站按 390px 宽度走查一遍（`app.module.css` 的 `max-width: 640px` 单列在手机上是全宽，桌面上是细长条，两边都要确认）；新增 `manifest.json` + 图标资产 + Service Worker 注册；推送授权的引导与开关放个人空间。
- **服务端**（`server/`）：新增推送订阅的存储与推送发送（Web Push 协议需要一对 VAPID 密钥，属配置不属代码）；在既有的通知产生点（`notification-service`）旁挂推送发送，**失败不得影响站内通知的产生**。
- **数据层**：新增推送订阅表（用户 × 设备端点）；订阅失效（端点 410）时 MUST 清理。
- **依赖新增**：一个 Web Push 发送库（服务端）；Service Worker 本身零依赖。
- **测试**：底部导航与未读徽标的 e2e；推送的单测用 fake sender（真实推送无法在 e2e 里稳定验证，同 `audio-scoring` 用 fake provider 的既有模式）；移动视口下的 e2e 走查（Playwright 设 390px viewport）。
- **基线依赖**：假定 `redesign-kindness-entry` 与 `add-shareable-blessing-card` 已 apply。本变更只动外壳与通道，不动它们定下的动线与产物。
- **本机限制**：iOS 的 Web Push 需要 16.4+ 且**必须先"添加到主屏幕"**才可用——真机验证需要用户在 iPhone 上实际装一次，和 B-69 的 Safari 录音复测一样属于只能人工做的一环。
