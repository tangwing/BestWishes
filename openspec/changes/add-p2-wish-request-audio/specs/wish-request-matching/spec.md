## Purpose

在公开广场之外，给祝福请求再开一条"被看见"的路径：系统按候选人的画像（位置、标签）主动计算谁可能愿意响应这条请求，推送通知给他们——这是 P1 受众筛选逻辑（`blessing-audience`）的镜像用法：那里是发送者选受众，这里是系统替请求人推荐候选人。

## ADDED Requirements

### Requirement: 发布时计算候选响应人

一条祝福请求发布时，系统 SHALL 用与 `blessing-audience` 相同的距离 + 标签匹配算法，计算出一批候选响应人（有位置画像的用户中，标签与请求关联标签有重合，或距离在合理范围内的）。候选人集合 MUST 在计算时定格快照，此后画像变化 MUST NOT 影响已经推送过的候选集合。

#### Scenario: 按标签匹配候选人

- **WHEN** 一条请求关联"考研"标签，某用户画像也有"考研"标签且设置了位置
- **THEN** 该用户被纳入候选响应人集合

#### Scenario: 候选人集合定格

- **WHEN** 请求发布后，一个新用户把标签改成与请求匹配
- **THEN** 该用户不会被追加进已经推送过的候选人集合

### Requirement: 候选人收到匹配通知

系统 SHALL 为每个候选响应人产生一条通知（复用 `notification` 的列表 + 未读机制），告知"有一条可能感兴趣的祝福请求"。此通知 MUST NOT 影响请求广场的展示——未被匹配到的用户仍然可以在广场看到并响应同一条请求。

#### Scenario: 候选人收到通知

- **WHEN** 一条请求匹配到 3 个候选响应人
- **THEN** 这 3 人各收到一条"有人可能需要你的祝福"通知，未读数增加

#### Scenario: 广场与匹配互不影响

- **WHEN** 一条请求匹配到 A、B 两人，C 没有被匹配到
- **THEN** C 仍然可以在广场看到这条请求并响应它

### Requirement: 无候选人时正常发布

系统 MUST NOT 因为找不到候选响应人而阻止请求发布——请求广场本身就是发现路径，匹配推送是锦上添花，不是必要条件。

#### Scenario: 零候选人

- **WHEN** 一条请求发布时没有任何用户的画像匹配
- **THEN** 请求正常进入广场，只是没有人收到匹配通知
