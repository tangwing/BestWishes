## MODIFIED Requirements

### Requirement: 统一人工复核队列

系统 SHALL 维护一个复核工单队列，来源包括：自动疑似、用户举报、用户申诉。每个工单的目标 SHALL 是一条祝福或一条祝福请求（`wish-request`）二选一——命中疑似的祝福请求（如处境描述带拉客 / 敛财话术）走同一个队列，不新建一套独立的复核机制。工单 MUST 记录目标（祝福或祝福请求）、来源、大类、状态、处理人、理由与时间线。队列 MUST 按优先级排序：高危举报 > 用户申诉 > 自动疑似 > 随机抽检。每个进入队列的工单 MUST 有终态（通过 / 下架 / 要求修改）。

#### Scenario: 复核通过

- **WHEN** 审核员对一条自动疑似工单判"通过"
- **THEN** 目标祝福转为 `published`，工单关闭并留痕处理人、时间、理由

#### Scenario: 复核下架

- **WHEN** 审核员对一条已发布祝福判"下架"
- **THEN** 目标祝福转为 `taken_down`，作者收到通知（含大类原因与申诉入口）

#### Scenario: 申诉二次被驳回

- **WHEN** 一条工单的申诉被资深审核员二次驳回
- **THEN** 工单关闭为终态并告知作者最终结果

#### Scenario: 复核通过一条祝福请求

- **WHEN** 审核员对一条命中疑似的祝福请求工单判"通过"
- **THEN** 该祝福请求转为 `published`，出现在广场，此时才计算候选响应人并推送匹配通知，工单关闭并留痕

#### Scenario: 驳回一条祝福请求

- **WHEN** 审核员对一条命中疑似的祝福请求工单判"下架"或"要求修改"
- **THEN** 该祝福请求直接进入终态，不曾公开过，工单关闭并留痕
