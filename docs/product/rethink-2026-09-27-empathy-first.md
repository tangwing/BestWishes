# 重新思考：从「祝福平台」到「共情 App」

> **状态：思考稿，未正式化。2026-09-27。**
> 本文件**不是**事实来源。[vision.md](vision.md) / [concept.md](concept.md) 仍然是当前生效的定位描述，**本轮尚未改动它们**——因为本文提出的几处调整与它们有直接冲突（见 §6「必须裁决的冲突」），需要用户拍板后才写进 vision/concept，重大的另开 ADR。
> 来源：2026-09-23 的第一性原理复盘 + 2026-09-27 用户补充的「共情 App」特性清单与调研方向。调研报告见 `docs/research/2026-09-27-*.md`。

---

## 0. 一句话结论

**把产品的统一对象从「一条祝福」改成「一件心事」——它的受益人可以是"我"，也可以是"我牵挂的人"。频次来自向内（为自己此刻的状态发一声），爆发来自向外（为所牵挂的人汇聚善意并送达）。**

这一条同时解决了两个此前互斥的问题：
- 上一轮复盘的结论是"为他人祈福 + 汇聚页 + 送达受益人"情绪强度和传播力最高（见 §2），但它是**episodic 的**——不是每天都有人要动手术，撑不起日活。
- 本轮用户提出的"寄托忧思、释放压力、秒级描述自己的状态"是**daily 的**，但单看它只是又一个树洞，缺少能引爆的社交对象。

两者不是路线选择，是同一条循环的两端。**不需要两个产品，只需要一个 `Event`（心事）实体 + 一个 `beneficiary` 字段（自己 / 牵挂的人）。**

---

## 1. 诊断：当前产品为什么没有爆点（2026-09-23 复盘）

三步路线（B-94/95/96）做的全是**减少摩擦**。摩擦不是爆点的来源；爆点来自**回报的强度、确定性与可见性**。当前三个结构性问题：

1. **能量梯度是反的。** 写祝福的人付出高、回报低且慢（"手有余香"是很微弱的内部奖励）；收祝福的人回报高但**完全被动**，不需要打开 App，也没有主动去要的路径。规律是：**强回报必须挂在用户需要反复做的那个动作末端。**
2. **没有"此刻的我"的入口。** 用户动机最高的那一秒（凌晨三点、手术前夜、忌日、刚失恋）需要的是**被安慰**，而产品当时对他说"祈福必须为他人而写，请先付出"。伦理漂亮，增长物理学致命。
3. **善意汇聚是收件箱，不是奇观。** "看见你收到的善意"排在 P4，被当成透明度功能——它**就是回报本身**。做成未读徽标，等于把烟花装进信封。

## 2. 第一性原理：两个需要同时押注的需求

问：什么需求是真实的、反复发生的、目前没有好产品的？

| | 向内（日频） | 向外（事件驱动） |
|---|---|---|
| 情绪 | 我此刻难受、压抑、没人可说 | 我爱的人正在受难，我什么也做不了（**无力感**） |
| 频次 | 每天，甚至一天多次 | 每次持续数天到数周，按人生事件与日历复发 |
| 强度 | 中，但持续 | 极高 |
| 时间压力 | 无 | **有 deadline**（手术是周二、高考 6/7）→ 每天回来看一眼 |
| 冷启动 | 只需要有人回应 | 零地理密度可用 |
| 传播力 | 弱（匿名内容不可转发） | **极强**（一个具体的人 + 一个具体的难处 + 可汇聚的支持 + 可转发的页面） |
| 合规 | 内容审核压力大 | 汇聚祝福而非钱款，绕开公开募捐红线 |

**结论：向内做留存，向外做增长。缺任何一半都跑不起来。**

向外那条的完整叙事（上一轮的核心发现，仍然成立）：
> 「我妈下周二做手术，我什么都做不了」→ 发起一件心事 → 眼看着素不相识的人一条条为她写下祝福 → 手术前一天，把这份汇聚起来的善意亲手交到她手里。

关键认知翻转：**发起的人不是捐赠者，他是最需要安慰的那个人。** vision.md 现在写"发起本身就是一种付出"，这误读了正在发生的心理过程，也压抑掉了唯一能让他天天回来的那股情绪。

## 3. 用户补充的特性清单：逐条按第一性原理评估

> 用户 2026-09-27 提出。下面不是复述，是评估——`✅ 采纳` / `⚠️ 采纳但要改设计` / `⛔ 建议不做或推迟`，每条给理由。

### 3.1 向外 · 表达自己的状态（✅ 核心，最高优先级）

秒级、最简输入、随时可操作。**这是整个新模型的入口，也是此前最大的缺口。**

⚠️ **但"纯自由文本框"是错的实现**。理由三条：空文本框是全世界摩擦最高的 UI；自由文本的审核风险和"比惨/卖惨"风险最高；没有结构化数据，匹配和推荐无从下手。

**建议形态：结构化极简输入。** 先选一个（情绪卡 / 天气隐喻 / 颜色 / 一组预制状态词），再**可选**补一句话，再**可选**补一段语音。
- 最快路径：**1 次点击**就能发出一条（"我今天很累"）。
- 语音是这里被低估的杀手锏：对不擅长打字的人更容易，被收到时情绪强度也更高——**而这套能力 P2 已经建好了**（`audio-*` 全链路）。

### 3.2 向外 · 看到别人的内容并表达善意（✅，但必须是阶梯）

不同的人用不同方式——正确。实现为一条**成本递增的阶梯**：
`一键加油（灯 / 抱抱）` → `接一句话 / 预制短语` → `自由文字` → `语音`

⚠️ 护栏（防止滑向廉价点赞）：**一键的"灯"只对接收方计数，不作为内容展示**（"37 个人为你点了灯"），只有写的 / 说的才进入内容流。一键是入口匝道，不是产品本身。

### 3.3 向内 · 回来先看到"我被加油了多少次"（✅ 这是清单里最聪明的一条）

它把"打开 App"的默认回报从社交焦虑翻成**被在意**。这是本产品与所有小红书式社区的分水岭：别人的社区首屏给你**别人的生活**（引发比较），这里首屏给你**别人对你的在意**。

⚠️ **但"系统先随机赠送 10 个"这句话有一个致命歧义，必须当场分清：**
- ✅ **可以**：送给新用户 **10 张"可以送出去的加油卡"**——降低首次给予的门槛，解决供给侧空转。
- ⛔ **绝对不可以**：伪造"别人给我的加油"来填充新用户的首屏。

伪造善意是这个产品**唯一不能碰的东西**。一旦被发现（一定会被发现），全盘信任瞬间归零，而信任是这个产品的全部资产。这是 vision.md「真诚是硬约束」的直接延伸。
→ 新用户首屏的冷启动问题，正确解法是 §3.5 的**供给分配 SLA**（保证真人回应），不是注水。

### 3.4 向内 · 付费与虚拟激励（⚠️ 方向对，机制要重设计）

"不要提现"是对的——一提现就变成资金业务，撞上 concept.md 已明确的二清红线，且立刻招来刷单灰产。

⚠️ 最大风险：**付费购买的善意，会让接收方觉得廉价**。设计原则：
- 钱买到的**不是善意的数量**，而是"付出的可见度 / 送出的能力扩容"（例：点一盏更亮的灯、为某件心事追加曝光让更多人看到）。
- **接收方永远看不到金额**，只看到"有人为你做了一件事"。
- 管理员批量发放要有**账本和上限**，否则通胀，"加油"很快一文不值（Reddit Coins 的教训已列入调研任务）。

### 3.5 Matching（✅ 但优化目标要换）

用户的表述本身很准："最终目的是大家看到的 event 都是最大可能激发善意的"——优化目标是**激发善意的概率**，不是点击率。这一条值得直接写进 spec。

⚠️ **但第一优先级不是推荐算法，是供给分配。** 冷启动期真正会杀死产品的是：**有人发了，却没有一个人回应**。那比不发更伤人，而且他再也不回来了。所以第一版必须有一条硬指标：
> **每条心事在 N 分钟内至少收到 1 条真人回应**（新用户的第一条，标准应更严）。

实现手段是分配而不是排序：把"还没有人回应的"优先推给正在浏览的人，并在 UI 上明说"这条还没有人回应过"。个性化推荐是有量之后的优化。

⚠️ 距离筛选在匿名产品里有**反匿名风险**（多次交叉可定位）。必须粗粒度（城市级 / 网格），不能给连续经纬度。

### 3.6 系统活动 · 集体祝福 / 头像与勋章（⚠️ 采纳，但要延后）

"精神 App 向健身 App 看齐"这个类比是对的（Keep / NRC / Strava 的挑战赛机制成熟）。

⚠️ **但冷启动期的集体活动，没人参加就是灾难**——而且用户自己已经指出 Keep 的问题是"内容太多、大杂烩"，那恰恰是过早堆功能的结果。
→ 早期用**全站聚合的仪式感**代替有名有姓的活动："今天，全站一起为 1,284 个人点了灯"。零参与门槛，永不冷清，而且它天然强化"我不是一个人"。真正的活动等有基础日活再上。

⚠️ streak / 打卡机制在情绪健康场景有**伦理风险**：连续天数断掉会让本来就低落的人更自责。要用"累计"而不是"连续"，绝不做惩罚性提示。

### 3.7 群聊的自治体系（⛔ 建议明确砍掉或推到很后面）

三条理由：
1. **与产品最核心的洞察直接冲突。** 现有设计反复强调"没有聊天、没有会话，善意是一来一回"——这是本产品最独特的取舍。一旦有群聊，它就变成了又一个社交 App，而社交 App 的赛道你赢不了。
2. **匿名群聊的治理成本是整个产品里最高的**，而且是持续的人力成本（Yik Yak 就是这么死的，已列入调研任务核实）。
3. "陪伴感"有更便宜的实现：**同行人的弱连接**——"此刻还有 23 个人和你一样睡不着"，可以互相点灯，但不能说话。要的是不孤单，不是聊天。

### 3.8 启动引导（✅，且作用被低估了）

了解偏好只是次要功能。onboarding 的真正作用是**设定社区规范**：这里不评价、不比惨、不给建议、只给陪伴。
在匿名 UGC 产品里，**靠 onboarding 灌输规范比靠事后审核便宜一个数量级**。

### 3.9 完全匿名（⚠️ 要精确定义）

"完全匿名"和"有积累"天然冲突——没有连续的自我，就没有 §3.10 的记忆资产。
**正确定义：对外匿名，对内有稳定账号。** 别人永远不知道我是谁（无昵称、无头像、无主页可翻），但系统里有连续的我，我能看到自己的全部历史。

→ 这与现有 `user-profile`（昵称 / 城市 / 性别 / 出生年，且 UI 到处展示 `authorNickname`）直接冲突，是数据模型和 UI 都要改的一处。

### 3.10 "不想让别人评价我，只需要同行人的陪伴"（✅，而且这一条有否决权）

这一条**直接否决了现有 AI 打分 / 精选 / 排行榜在用户侧的展示**：
- AI 反馈只能用于"帮**给予方**把话说得更完整"，且**可关闭**。
- **接收方侧永远不展示任何分数、标签、等级。**
- vision.md 的「精选」机制要重新考虑——正向策展在"不被评价"的承诺下依然可能成立（精选是**给旁人看的展示**，不是**对作者的评判**），但必须重新设计呈现方式。

### 3.11 历史即记忆（✅ 被低估，是最难被抄走的资产）

"历史的数据能代表美好的记忆"——这是"积累"的正确形态：不是积分，是**记忆**。
> "一年前的今天你写下'撑不住了'，那天有 13 个陌生人陪着你。今天的你怎么样？"

这是日记 / 自我关怀类产品（Finch、Day One）留存的核心，也是**唯一无法被竞品复制的东西**（数据在用户自己身上）。它同时给了一个天然的年度时刻（年度回顾 = 自带传播）。

## 4. 由此推出的产品骨架（替代原三步路线）

### 4.1 统一的数据对象

```
Event（心事）
├─ beneficiary: 自己 | 我牵挂的人（名字/称谓）   ← 一个字段打通"向内/向外"
├─ 结构化状态（情绪卡 / 场景）+ 可选一句话 + 可选语音
├─ occasion & deadline（手术 / 考试 / 忌日；可空）  ← 制造紧迫感与回访
├─ 匿名（对外恒匿名；对内属于稳定账号）
└─ 回应（阶梯：灯 / 短语 / 文字 / 语音）
     └─ 汇聚产物：可分享页 + og:image（受益人是他人时可"送达"）
```

现有 `WishRequest` 就是这个对象的雏形，`Blessing(scope='wish_response')` 就是回应。**改造量远小于重写**——主要是放开"必须为他人"的约束、加 `occasion/deadline`、加结构化状态、把身份展示改成匿名。

### 4.2 五个关键设计（按杠杆排序）

1. **一屏两动作**：首屏 = ①我被加油了多少次（回报前置）②此刻的我怎么样（1 次点击可发）③有人在等你（未被回应的心事）。
2. **回应阶梯 + 一键不计入内容**（§3.2）。
3. **供给分配 SLA**：保证每条心事都有真人回应（§3.5）。这是生死线，不是优化项。
4. **真人回执**：告诉给予方"你的话被 TA 读了 / TA 回了一句"。AI 反馈是教练，不是奖励；只有真人的回应能强化再给一次的行为。
5. **汇聚与送达 + 记忆**：向外那条的高潮（把陌生人的善意交到受益人手里，受益人由此成为新用户）；向内那条的沉淀（周年回望）。

## 5. 技术选型 Review（用户问"是否要重新开始"）

**结论：不要重新开始。资产比想象中多，要换的恰好是最便宜的那一层。**

| 模块 | 行数 | 在新模型下的命运 |
|---|---|---|
| `server/src` | 7,511 | **绝大部分保留**：auth/session、consent、审核管线+队列、notification、inbox、audio 全链路、blessing 状态机（hold→扫描→送达）、report、audience 匹配（haversine + 标签 → 变成 matching 的基础） |
| `packages/domain` + `shared` | 2,082 | **保留**（纯函数 + Zod schema，跨端复用的初衷在换端时才真正兑现） |
| `client/src` | 3,278 | **这一层才是要重做的**，且它最便宜 |
| `e2e` | 660 | 用例要重写，框架保留 |

要改造的服务端部分：`WishRequest` → `Event`（放开受益人约束 + occasion/deadline + 结构化状态）、新增**加油卡账本**、身份展示匿名化、审核升级（见下）。

### 5.1 ADR 0003「Web-first PWA」确实需要重审

**理由是新模型的命脉变了**：留存完全依赖推送（"你被加油了 12 次"这条通知就是产品的心跳）。而 iOS 的 Web Push 要求 16.4+ **且必须先手动加到主屏**（B-96 已记录这个限制），转化率极低。**不能把产品心跳建在这上面。**

| 方案 | 取舍 |
|---|---|
| **Expo / React Native**（倾向） | TS + React 心智直接复用；`packages/domain` / `shared` 可直接 import（这是当初分包的真正回报）；`expo-notifications` 推送、`expo-av` 录音都是成熟路径；能上应用商店（有 App 才有"精神健康 App"的身份）。代价：多一套构建与发版流程，iOS 需开发者账号与审核（心理健康类目审核更严）。 |
| 继续 PWA | 零迁移成本，但 iOS 推送受限 = 放弃留存主引擎；且"随时秒级打开"在浏览器里体感明显更差。 |
| 微信小程序 | 中国大陆情绪类产品的真实流量在微信里、免安装、有复访位；但**订阅消息**极受限（一次性授权、类目限制），做不了"你被加油了"这种高频推送；"心理健康"类目有资质要求；且无法承载完整的匿名情绪社区风险。→ **定位为传播补充，不是主端。** |

**建议的终局形态：`Expo RN App`（用户主体验 + 推送）+ `保留极薄的 Web 落地页`（微信内转发 / 汇聚页 / 受益人免安装打开）。** 这正好契合"汇聚页要能在微信里转发给妈妈"的需求——受益人不该被要求装 App。现有 `client/` 不删，收缩为这个落地页。

**不需要重审的**：Node + Fastify + PostgreSQL + Drizzle + pnpm monorepo（D4/D5/D6/D7/D8）全部继续有效；PGlite 开发、生产换驱动一层。

### 5.2 一个用户没提但必须提的硬要求：危机干预

"寄托忧思、释放压力"+ 完全匿名 = 一定会收到**自伤 / 自杀倾向的内容**。这不是概率问题。

- **审核从 P2 模块升级为产品生死线。** 当前 demo 默认 `always_pass`（B-82，当时是对的权衡），但新模型下内容量暴增且更敏感。
- 必须有**危机干预路径**：识别到风险表达 → 立刻展示求助热线与资源 → 进人工优先队列 → 相关内容的回应端要有引导（不许说"想开点"）。海外同类产品（7 Cups / Koko / TalkLife）全都有这一层，且有公开的伦理争议史可借鉴（已列入调研任务）。
- 这一层的缺失是**唯一能让产品在一夜之间关停**的风险，优先级等同于核心功能。

## 6. 必须裁决的冲突（等用户拍板，拍板后才改 vision/concept + 开 ADR）

1. **「祈福 MUST 为他人而写」是否放开？** vision.md 现在是硬规则（B-97 刚强化过）。§0 的统一模型要求放开为"受益人可以是自己或牵挂的人"。**这是本轮最根本的一处改动。**
2. **「发起者是付出方」是否改为「发起者是情绪需求方」？** 影响 vision.md 的价值主张段落与全部文案调性。
3. **完全匿名 vs 现有画像模型**：`user-profile` 的昵称/城市/性别/出生年要不要保留（保留则只用于匹配、永不展示）？现有 UI 大量展示 `authorNickname`，要改。

## 7. 下一步怎么推进（建议的新路线，替代 B-94/95/96 的排序）

> 顺序有依据：先裁决（避免边写边改方向）→ 先用最便宜的方式验证情绪是否成立（Web，不碰 RN）→ 再改数据模型 → 再换端。

- **第 0 步 · 裁决与记录（不写代码）**：§6 的 7 条逐条定，结论写进 ADR（至少两份：`模型统一：心事与受益人`、`端形态：RN + Web 落地页`），同步更新 vision.md / concept.md。
- **第 1 步 · 情绪验证（仍在现有 Web 上做，刻意不上 RN）**：把"一屏两动作"做出来（发布状态 / 回应别人 / 回来看加油），自己连续用 3-7 天，找 5-10 个真人用。**要验的是"发出一条 → 收到真人回应 → 情绪真的被接住了"这件事是否成立**——这个验证不需要推送，也不需要原生壳。若不成立，换端也救不了。
- **第 2 步 · 模型统一 + 加油卡账本 + 匿名化**（服务端改造，见 §4.1 / §5）。
- **第 2' 步 · 审核与危机干预**（与第 2 步**并行，不可延后**，见 §5.2）。
- **第 3 步 · 端形态**：Expo RN + 推送；`client/` 收缩为分享落地页（原 B-96 的 PWA 壳被它取代）。
- **第 4 步 · 汇聚与送达**（原 B-95 的可分享产物，对象换成"一件心事的汇聚"）。
- **第 5 步 · 记忆 / 回望 / 全站仪式感 / 勋章**（§3.11 / §3.6）。

**B-87（trace 系统）从"未来计划"升级为第 1 步的前提**——第 1 步要验证的三个数必须能量出来：① 一条心事在 N 分钟内收到首条真人回应的比例 ② 发布者当天回访率 ③ 回应者的二次回应率。没有这三个数，第 1 步的结论就是感觉而不是证据。
